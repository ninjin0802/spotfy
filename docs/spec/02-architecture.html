2. アーキテクチャ

画面・ブリッジ・Web Player の 3 層と、その間のデータと操作の流れ。

2.1 全体構成

2.2 層と責務

層主なファイル責務
ネイティブ UINativeApp.kt ほか画面の表示と操作。データは Bridge から受け取り、端末側の機能は AppHost 経由で使う
ホストMainActivity.ktWebView の生成と設定、ページとの通信の受け口、通知・バックグラウンド・設定・エラー表示・アップデート
ブリッジ（アプリ側）Bridge.ktページのメソッドを suspend 関数として呼ぶ。結果を型（Card・Page など）に直す。再生状態などを StateFlow で配る
ブリッジ（ページ側）bridge.jsWeb Player の登録簿・GraphQL を呼んでデータを作る。再生状態を送る。広告・クロスフェード・ギャップレス
下支えpolyfill.jsページの読み込み開始時に入る。MediaSession の代用、アプリとの窓口（__native）、Connect の通信の送り直し
再生エンジンSpotify Web Playerログイン状態・データ取得・再生（DRM）・Connect

2.3 データの流れ（読み込み）

  1. 画面（例：HomeScreen）が bridge.home() を呼ぶ
  2. Bridge.call("home") が ID を振り、__mb.call(id, "home", args) をページで実行する（evaluateJavascript）
  3. bridge.js の methods.home が Web Player の GraphQL ローダー（gql()）を呼び、結果を軽い JSON に整える
  4. ページが {type:"bres", id, ok, value} を AndroidBridge.postMessage で返す
  5. MainActivity.onPageMessage → Bridge.onMessage が待っている呼び出しを再開し、HomeFeed などに直して返す

2.4 状態の流れ（再生）

  1. bridge.js は PlayerAPI の update イベントと 1 秒ごとのタイマーで snapshot() を作る
  2. 前回と変わっていれば bstate（画面用）・playing（サービス用）・meta（通知用）を送る
  3. Bridge が player: StateFlow<PlayerState> を更新し、ミニプレーヤー・全画面プレーヤーが描き直される
  4. MediaControls が通知とロック画面の表示を更新し、PlaybackService がバックグラウンド再生を保つ

2.5 操作の流れ（通知のボタン）

通知のボタン → MediaControls.Receiver → MainActivity → window.__mMedia(action, pos) → PlayerAPI.resume / pause / skipToNext / skipToPrevious / seekTo。

2.6 設計の判断

判断理由
ページの画面は使わず、ネイティブ UI を重ねるv1 はページの見た目を組み替えていたが、重く壊れやすかった。データだけ取り出して自前で描くほうが軽く、公式アプリに近づけられる
Web Player 自身の GraphQL ローダーを使うログイン情報・トークンの扱いを Web Player に任せられる。公開 Web API は 429 になる
デスクトップの Chrome を名乗るモバイル UA だとアプリのダウンロード案内に飛ばされ、再生デバイスとして動かない
WebView を常に「見えている」扱いにする裏に回るとページのタイマーと再生が止まるため（AwakeWebView）
ページは描かない（content-visibility: hidden）見えない画面の描画をやめて電池を節約する
Connect の通信は端末から送り直すWebView が付ける X-Requested-With で再生コマンドが拒否されるため（ConnectRelay）
